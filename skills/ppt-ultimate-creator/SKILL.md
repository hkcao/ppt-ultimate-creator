# 终极ppt生成

## 交付目标

交付内容准确、结构可编辑、与用户确认视觉稿基本一致的 `.pptx`。优先级：内容准确 > 语义结构与编辑性 > 视觉还原。允许少量视觉差异，逐页说明具体影响，不承诺像素级一致。

整页 AI 图片是视觉参考，不能成为最终 PPT 的整页背景替代全部对象。确认的文字、数据、关系与来源独立保存在逐页规格中；重建同时读取规格和图片，不从图片 OCR 重新决定事实。

## 开始与续做

- 新项目先阅读足以理解关键原理的资料，简述机制、证据和未知项，实际发起一次合并的启动确认：有缺口则澄清，信息齐备则展示理解摘要及参考模板选择供确认。缺口未解决不得直接写逐页大纲或内容布局。优先使用当前可用的 ask / request_user_input 类工具（遵循工具模式限制）；没有工具时用普通回复提问。未收到必要回答前，只做来源阅读、提取和缺口整理。
- 初始澄清合并询问是否有希望参考的模板、已有 PPT 或风格图片；已有明确模板则直接使用，不重复问。不默认先推荐模板。用户说没有、让你推荐或明确委托决定时，再按用途给少量风格建议，与大纲/HTML 一起确认，不新加独立确认轮次。
- 先核对用户期望呈现的范围、深度、受众与目的；用户已明确的信息不重复问。信息齐备时不重复问已知字段，但仍完成一次启动确认；仅用户明确说无需交互/直接全流程制作，或续做已有有效确认时跳过。次要样式用已规定默认值，并在预览中展示；不能把默认值用于补造实验事实。
- 尊重指定输出目录，否则在当前工作区创建独立项目目录，避免覆盖已有文件。
- 续做先读项目 `state.json`、`brief.md`、`slides.yaml` 和确认记录，定位受影响页面。不要重新询问已确认且未变化的事项。
- 默认采用下述精简确认流程，六阶段是内部工作步骤，不是六次等待；同一条回复可确认多个已展示产物。记录用户原话和对应版本，不将沉默、超时或初始“帮我制作”当作后续视觉稿已获批准。用户明确调整或跳过阶段时记录并遵循。
- 在阶段内完成可独立执行的工作，再展示具体草稿与聚焦问题。只等待影响下一阶段的选择，不为工具选择或普通修复重复询问。
- 调用前确认真实 AI 生图和 PPTX 生成、渲染能力可用；缺少能力时说明受影响阶段，保留已完成工作。不能把 HTML 截图冒充 AI 视觉稿，或把未渲染 PPT 宣称校验通过。图像能力按下述规则选择，不依赖特定平台或 GPT 图像模型，不额外设置后端批准关卡。

## 确认必须实际等待（所有 Agent 通用）

ask 只是交互界面，不是确认机制的前提。有可用工具就调用并等待真实回答；没有 ask、工具返回空值或宿主无交互工具时，向用户发送普通问题并结束本轮回复，停在 `waiting_for_user`。不能在问题后继续生成下一阶段，不能以“默认同意”“自动确认”或工具不可用绕过等待。

启动确认、大纲+HTML 确认、样张确认分别记录产物版本及用户原话。没有对应答复就不进入依赖阶段；只可继续不依赖该答案的资料核实。若宿主只允许无人值守执行且不能暂停，交付待确认摘要并说明后续阶段未运行，除非用户已明确授权免交互模式。不得声称已调用不存在的 ask 工具。

## 平台无关的图像能力选择

- 尊重用户指定能力/后端和宿主运行规则；否则优先使用当前模型或 Agent 已有能力，包括原生多模态输入、原生图像输出、宿主提供的图像工具。非 Codex 环境也不要求安装 Codex 工具、切换 GPT 或配置 OpenAI API。
- 分别检查识别、生成和编辑能力：能读取图片不代表能生成或编辑图片。看图、理解原文图表和视觉对照可直接用当前模型的视觉输入；仅需准确文字/数据时优先文档解析，必要时补充已有 OCR，不强制额外调用视觉 API。
- 当前模型能实际输出图像文件或可保存的图像结果时，直接用于 AI 视觉稿；能编辑时直接用于局部迭代。不能仅凭模型名或“多模态”标签宣称支持，不能把文字描述、HTML 截图或未执行的调用当成生图成功。
- 仅在所需能力缺失或不满足任务时，按 [外部生图](references/image-backend.md) 使用用户配置的 API 或其他实际可用适配器。随附兼容 Images API 脚本只是可选路径，不是统一入口；已有原生能力无需经过它。

## 默认确认节奏

默认共 3 个合并确认点，避免逐页重复询问：

1. **启动确认**：简述原理理解、范围/深度、受众/目的及参考模板选择；一次合并询问，已有答案直接沿用。用户明确免交互或已有启动批准时才跳过。
2. **内容与布局合并确认**：需求明确后一起制作大纲与 HTML，在同一份预览中展示逐页标题、证据、布局及默认样式，一次确认，不先等大纲再等 HTML。
3. **代表性 AI 样张确认**：确认风格后自动扩展全套、冻结生成参考版本、重建 PPT、渲染 QA 并交付。全套图片仍可查看，但默认不另设“全部图片批准后才重建”的等待。

自动扩展页面标为 `generated_reference`，不能冒称用户逐页批准；用户批准样张只记录样张版本和风格。重大内容/风格偏离、证据缺失或编辑性取舍才暂停集中提问。正常修复、符合规格的扩展以及交付不新增确认；用户反馈可继续迭代。用户明确要求逐阶段/逐页确认时切换详细模式，遵循其指定节点。

## 六阶段流程

### 1. 确认内容来源

读取用户指定范围：目录先做清单，明确相关子目录与排除项；文档/论文记录页码或章节；网页实际读取并记录链接及访问日期。区分“内容来源”和“风格模板”。无法读取、缺图、数字矛盾或依据不足时明确列出，不以标题或摘要猜测全文。

实验结果、数据和结论必须定位到实际读到的原文页码、图表号或网页段落。按可读性选择保留原图、增加直白图例/局部放大或基于核实数据重绘（含必要图例、单位、条件）；截图不是硬规则，按 [证据与并行执行](references/execution.md) 保存来源。无法读取原文时请求资料或标为待核实，不用常识、摘要推测或 AI 图补齐结果。

整理来源与关键原理理解，完成合并启动确认后进入阶段 2 的大纲提案；有缺口问缺口，信息齐备则确认摘要。不自行扩展到无关目录或将额外网页研究视为必需。

### 2. 需求、模板与逐页大纲

读取 [交互与项目记录](references/planning.md)；选择模板时读取 [模板库](references/templates.md)，规划视觉时读取 [设计方法](references/design-methods.md) 的通用原则与类别索引，只加载当前汇报类别对应的样式/布局文档，不要为每页重复加载。

- 模式 A：用户给出每页标题、内容及呈现设想；保留其意图，整理并指出缺口/冲突。
- 模式 B：用户主要给出资料；先提出启动理解摘要，有缺口时附需求选项；收到启动确认后，再起草整套大纲及逐页表达方案，交给用户修改确认。两种模式可混合。
- 默认中文字体为微软雅黑（Microsoft YaHei），英文为 Times New Roman；涉及数学表达的内容必须以“插入公式”方式创建可编辑原生公式对象（如 OMML），并使用实际可用的数学字体；普通文本、Unicode 拼式和公式图片都不算满足，不强套正文字体；混排按文字 run 指定，检查生成与渲染环境字体。缺字库时告知具体替代及影响，不宣称已用指定字体。明确的用户/品牌字体要求优先。
- 澄清受众、目的、现场讲述或自主阅读、技术深度、时长、页数、比例、语言、模板/风格、必须保留内容及编辑要求。为整套建立清楚主线，每页只承担一个主要沟通任务；不把所有标题强改成结论句。
- 浏览模板库，推荐少量相关模板；明确品牌固定项与可变布局。工作汇报且用户无指定模板时，默认采用 [工作汇报指南](references/styles/work-report.md) 中的华为浅色 16:9 模板；其他类别无模板时给出对应风格建议。
- 逐页整理并在合并预览中确认标题、核心信息、依据、图表/示意图类型、大布局与素材。明确总页数是否含封面，避免擅自增加页数。

**默认不单独等待：** 启动已确认后继续阶段 3，将大纲与 HTML 合并展示确认。

### 3. HTML 内容与布局草稿

制作可在浏览器打开的 HTML，画幅比例与 PPT 相同，逐页可浏览。使用真实关键文字、数字和关系，图片占位需标明。HTML 用于调整叙事、层级、布局及表达方式，不假装是最终视觉稿。

展示或打开实际 HTML，检查溢出及可读性。用逐页浏览和缩略总览检查主线、布局节奏及重复内容；字体层级、配色、边距和图形规范写入 brief，供生图与重建共用。汇总需决定的内容删改、页序、图文关系和布局变化，更新规格。

**合并确认点：** 大纲、当前 HTML 版本的内容和大布局。HTML 确认不等于批准尚未生成的 AI 图片。

### 4. AI 高保真视觉稿与迭代

先选一张代表性内容页作为样张，封面不是默认样张。用当前模型的原生图像生成能力或实际可用的 AI 生图工具，以确认的 HTML 布局、模板参考及逐页规格生成图片。HTML 截图可作为生图输入，最终视觉稿必须是真实 AI 生成/编辑结果，不要求调用特定厂商工具。

样张确认后再生成其余页。复用配色、字体层级、图形语言与固定品牌约束，按页面角色变化布局。复杂且难以原生重建的效果在样张阶段就提示或简化，避免全套重建后才暴露问题。

样张包含复杂原生图表、连接关系或特殊字体时，先做对应局部的临时可编辑实现与渲染检查，以验证重建能力；它不是提前交付的最终 PPT，也不新增用户确认关卡。确认的图片、提示词、素材和设计规格复用到后续页面，局部改动只重做受影响页。

数字、文字和技术关系以规格为准，生图不构成新证据。需原样保留的 Logo 或截图引用原始素材；论文图按证据规则保留或确定性重绘，禁止用 AI 随意重画数据曲线。保存每页提示词、参考素材、实际使用的模型/工具、返回图片位置和版本。

全套视觉稿保存并提供查看入口，主 agent 对照规格与样张检查，通过后自动继续重建；不等待用户逐页批准。用户可对任意页反馈。优先编辑受影响图片并同步内容变更，支持多轮交互。默认每次反馈最多做两轮自动修复尝试，再展示结果和剩余差异；用户新反馈后继续迭代，不无限重生成。

**确认点：** 代表性样张。全套图片通过内部检查后冻结为生成参考版本；不能悄悄重生成参考图来掩盖 PPT 差异。详细模式按用户要求等待全套确认。

### 5. 重建可编辑 PPT

读取 [原生对象与对比验收](references/editability-and-qa.md)。以确认的 `slides.yaml`、模板约束和冻结参考图片共同为输入，制作原生文字、形状、连接符、图表、表格和独立图片。

多页执行按 [证据与并行执行](references/execution.md) 分配独立页面给 subagent；确认、共享规范和最终组装由主 agent 负责。

使用当前环境实际可用的 PPTX 生成库及 API，先使用环境提供的依赖发现工具。如有适用的 presentations 技能，按需读取其实现/渲染说明；本技能不依赖特定旧技能、固定插件版本或不存在的 CLI。明确要求可编辑的图形和图表必须用原生对象实现。原文实验图表可按表达需要保留或重绘；原图保留是明确的编辑性例外。图例不直白、字号过小或对比不清时，先考虑重标注或重绘，仅用核实原始数据重建，禁止从曲线像素估数。没有逐点数据时保留原曲线并加直白标注，或请求数据，不因审美编造数值。

正式构建前验证一条复杂原生公式的插入、保存和实际渲染，不能只口头承诺支持。能力不足时寻找可用实现；仍不可用则明确未满足原生公式要求，不擅自降级为图片。

一个语义元素使用合适的对象：数据折线用原生图表，折线路径优先单个连接符/自由曲线；不要用多线段拼接或逐字拆分文本。照片、截图及复杂插画可用独立图片，不能声称其内部可编辑。

正常制作与修复自行完成；需要牺牲内容、关系或重要编辑能力时，展示具体替代方案再请用户决定。

### 6. 渲染、对比、修正与交付

实际渲染 PPTX，逐页对照确认图片和内容规格。分别检查内容准确、视觉一致与原生编辑结构。程序检查和目视检查互不替代。包含公式的页面要核对原生公式对象；图形需同时检查画布边界和所属内容容器，子元素未出幻灯片但越出卡片也属于排版问题。

先修内容和编辑结构，再调视觉。针对同一问题默认至多两轮自动修复与重新渲染；仍有重大差异或无进展时列出页面、证据和选项，请用户决定。小差异可交付时说明；事实错误、缺页、关键关系错误或应原生编辑却被贴图不得算完成。

交付最终 `.pptx` 和简短使用说明，列出残留差异及图片对象边界。保留 HTML、确认稿、规格、生成源代码和检查记录供续改，除非要求，不把全部临时文件堆在最终回复里。只有实际在 PowerPoint 打开检查过才说“已在 PowerPoint 验证”。
